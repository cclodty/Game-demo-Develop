## 1. 摘要

**現在在哪裏（2026-10-22）：** 原本排到明年五月的四個階段，十月中到十月廿二日已做到第四階段 ①。一局有頭有尾（街機 12 波、評級、每張圖的頭目），有每天回來的理由（每日挑戰、成就、重播），有七張澳門地圖和「澳門一夜」，也有手掣和手機的第一版。遊戲在 GitHub Pages 上，完全離線。

**2026-10-22 開發者的五個決定**（DECISIONS.md 同日各一行）：

1. **不設試玩關卡。** 找不到人試玩，所以原本每階段之後的試玩關卡跳過。新手熱身、操作提示、每波之後的提醒就是現在這樣，夠用。往後的驗收是開發者自己試玩（N 記一筆、匯出回饋）。
2. **39 個模型全部重新審視。** 有些太簡陋，不能見人。逐個決定留、重做、還是退回方塊版（§11）。
3. **第五階段做手機操作。** 新地圖和地圖互動都等開發者的地圖量體與生成：量體做完之後，像議事亭一樣由它拿一部份做地圖，再按地圖設互動件（§6）。賭廳、燈塔因此由第四階段 ② 移到那時候。
4. **「澳門一夜」不加地圖。** 開發者對一夜沒有特別想法；Claude 的建議是做完它但做細：只補一個結尾（收尾對白、一夜的結算、一個成就），不補 04:00、05:00。之後由量體來的新地圖有時間就自動排進去。
5. **後端不部署，上架未定。** 排行榜只在本機；後端程式和 `docs/BACKEND.md` 留着，`config.js` 的 `BACKEND.url` 留空。

**完工的定義**（開發者 10-22）：量體地圖與互動、修正模型這兩大方向做完，遊戲就算完工；加上已排的第四階段 ② 和第五階段「手機」，一共四步（§10）。

**接下來：** 第四階段 ②（`docs/GOAL.md`：兩個頭目、一夜的結尾、模型審視）→ 模型修正 → 第五階段「手機」→ 量體做完時：量體地圖與互動 → 完工。

**定位一句話**（不變）：在真實比例的澳門街頭跳一場子彈芭蕾。真實澳門地景是別的遊戲沒有的賣點。

## 3. 設計支柱

往後每一個新功能都用這四條原則衡量；不符合任何一條的，就不做。

1. **打得漂亮比打得多重要。** 分數、評級、解鎖都獎勵花式和多樣性，不獎勵躲在角落打點射。每個新敵人、新武器都要能製造新的「漂亮」。
2. **子彈時間是解題工具，不是無敵按鈕。** 新敵人要是一個「題目」，玩家用慢鏡看清楚再解；不要讓慢鏡變成每波必開的保命符。
3. **真實澳門是賣點。** 新地圖優先選有辨識度的澳門地點，每張地圖要有一個只有那個地點才有的機制。沒有地方特色的地圖不做。
4. **一局十分鐘，每一局都有得著。** 結束時玩家要帶走三樣東西：一個評級、一段可以分享的片段、一個向解鎖前進的進度。失敗也要有得著。

**三條線**（第三階段起，開發者試玩後定的）：每張卡都要答得出「玩家多了一個什麼漂亮的解法」，答案落在其中一條：**打得精彩**（敵人會躲會包抄、波次有拍子、Style 獎勵推進）、**地圖會說話**（互動件、舞台、每張圖自己的機制）、**不開槍也能打**（踢、擲、工具、環境）。

### 第五階段「手機」（第一版清單，寫卡時再定）

目標：開發者用自己的手機玩完一局街機，不用碰鍵盤，而且可以由手機交回饋。

- **其他動作的觸控按鈕：** 旋轉、滑鏟、踢、擲、換武器、處決、飛撲、人盾；右搖桿旁一排小按鈕，或手勢（例如雙擊旋轉、向下掃滑鏟）
- **觸控的提示：** HUD、熱身、每波提示都講觸控的做法，不寫鍵盤鍵（現在 FOCUS 旁寫「Shift/Q」、彈藥用盡寫「G 擲出」）
- **選單用手指操作得到：** 標題、暫停、結算、設定的按鈕夠大；直放時提示轉橫
- **手機上的回饋：** 觸控沒有 N 鍵：暫停選單要有「記一筆」（匯出已經在暫停選單），回饋附上真機的幀率（`perfLine`）
- **真機效能：** 用開發者的手機量幀率，按結果加第三檔畫質或再減繪製
- **全螢幕和手勢：** 全螢幕、鎖橫向、防止雙擊縮放和下拉重新整理
- **這次不做：** 上架、原生 App；震動排在最後

- 判了「重做」的，按 `assets/SPEC.md` 和 `assets/PROMPTS.md` 寫新的說明（尺寸、骨架、原點、貼圖、預算），連同「哪裏不行」的截圖
- 這張卡不做：重做模型本身

### 模型修正（開發者判完之後）

- **Claude 修：** 能在資產流程用程式修的：尺寸、原點、朝向、材質數、顏色、面數（`npm run assets` 和 `src/asset-manifest.js` 的預算）
- **開發者做：** 要重新生成或重建的（形狀不對、太簡陋）：用工具重做或外判，按審視寫好的說明
- **退回方塊版：** 刪掉那個模型檔，遊戲自動用回方塊版
- 完成的標準：每個留下來的模型，開發者看過都覺得過得了眼

### 重做從哪裏來

| 方式 | 大約費用 | 優點 | 缺點 |
|---|---|---|---|
| AI 生成工具 | 每月 US$20–80 | 便宜、快 | 質素不穩，綁骨和動作弱；2026-10-15 的測試已證實；現有模型有些就是這樣來的 |
| 外判自由工作者（ArtStation、Fiverr、本地美術） | 人物連綁骨和動作每個約 US$300–1,500；道具每件約 US$30–150 | 質素可控，可要求源檔 | 要寫清楚規格，有來回修改 |
| 合約美術一個月 | 約 US$2,000–5,000 | 風格最一致 | 要有足夠的工作量填滿一個月 |

如果要花錢，先做的仍是玩家每一局都看見的：主角、打手、刀手、手槍、散彈槍、步槍，和幾張圖共用的道具（木箱、油桶、氣罐、平底鑊、路障、貨櫃）。地標建築、背景樓宇、地面材質暫時不買：程序生成的已經獨特而且比例準確，玩家在 30 米外看不出分別。

### 避免白花錢

1. 用 `assets/SPEC.md` 和 `assets/PROMPTS.md` 做說明書：尺寸、骨架、原點、貼圖格式已經定好，不會做完才發現放不進遊戲。
2. 先做一件，放進遊戲看，再批量。
3. 全部人物用同一套骨架，動作可以共用。
4. 合約要求交 Blender 源檔、分層貼圖和商業授權。
5. 新模型要過渲染預算：材質少、網格會在載入時按材質合併（`models.js`）。
6. 方塊版永遠保留為後備，任何模型出問題都能退回。

## 12. 風險與對策

最大的風險仍然是範圍：每一節都有十件想做的事。

| 風險 | 後果 | 對策 |
|---|---|---|
| 範圍膨脹 | 做了很多，沒有一樣完整 | 一張卡一天、有「這次不做」；四條支柱和三條線；發現的事寫進待排，不順手做 |
| 沒有試玩者 | 手感只有開發者一個人判斷，盲點看不到 | 本機事件記錄和回饋匯出；每階段把「待試玩確認的數字」列齊；機械人測試量一局的長度和難度 |
| 模型質素 | 簡陋的模型令第一眼更差 | 模型審視與修正（§11）；方塊版永遠是後備 |
| 量體未完成 | 完工的最後一步取決於開發者的量體進度 | 其餘三步（第四階段 ②、模型修正、手機）不等量體，先做 |
| 手機效能 | 在中階手機上掉幀 | 手機預設低畫質，繪製次數已減六至九成；第五階段用開發者的手機量 |
| 真實地點的敏感性 | 在真實地標開槍可能被批評 | 風格化；不用真實品牌、招牌、人名和事件；敵人是虛構幫派；「漆彈模式」（沒有血）在待排，上架前做 |
| 單檔大小 | 超過 16 MB 的分享上限 | 現在約 11 MB；GitHub Pages 是多檔寄存，模型分開載入 |
| 成本 | 伺服器和美術費失控 | 後端不部署，沒有伺服器費；美術錢等模型審視之後再決定 |
| 一人開發的節奏 | 幾星期沒有可見進展就會停下來 | 每階段合併上線一次，開發者即玩 |
| 授權 | 地圖資料、字型、音樂的授權問題 | OSM 已署名（ODbL）；Google Fonts 可商用；音效和音樂是程式合成；模型要有商業授權 |
