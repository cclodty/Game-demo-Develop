# 製作資源準備計畫

版本：0.2｜依360°瞄準及人物平滑轉身更新｜2026-09-25

本文件承接《末日生存遊戲企劃初稿》及《第一個可玩版本：三人逃難序章》。使用者已決定劇情細節稍後處理，現在先細分製作所需資源，準備回家後開始工作。

目前已具備企劃文件。使用者確認家中為 Windows、64GB RAM、RTX 4090，已安裝 Godot；初期使用免費工具、暫用素材與現有圖像生成額度。尚未建立 Godot 遊戲專案、取得正式素材或在家中電腦實測。以下數量、工具組合及尺寸均為製作提案，不代表已確認的遊戲規格。本次只準備文件，未啟動 Goal。

## 1. 準備工作的完成點

資源準備的第一個完成點，是能開始製作「小型操作測試場」。它需要主角、測試敵人、槍械、地面、牆、障礙與操作介面。三人逃難序章仍是第一個可玩版本；操作測試場是它的第一個製作步驟。

把資源分為三批，按用途取得：

| 批次 | 支援成果 | 資源要達到的程度 |
| --- | --- | --- |
| R1 操作測試包 | 移動、固定跟隨鏡頭、瞄準射擊、遮擋、有限子彈時間 | 形狀及狀態清楚、能匯入與使用；可全部暫用。 |
| R2 序章功能包 | 三人行動、步行相連路線、互動事件、完成與重試 | 所需角色、物件及資料都有固定識別碼，能完整走過流程。 |
| R3 表現替換包 | 正式模型、像素材質、動作、音效、可讀介面 | 已通過比例、連續轉身、畫風、來源及遊戲內呈現檢查。 |

劇情尚未定稿時，R2 可以用「救援事件甲」「提示事件乙」等功能標籤測試；不能把這些暫用內容視為正式劇情。正式敘事體驗的驗收留待劇情決定後完成。

## 3. 正式素材前，先固定這幾項規格

### 3.1 2.5D 的實作選擇

2.5D像素風、固定朝向跟隨鏡頭是已確認的視覺方向。使用者進一步確認鍵鼠360°自由瞄準，而且整個人物也要連續平滑轉身。

| 路線 | 主要需要的資源 | 需要驗證的難點 |
| --- | --- | --- |
| 2D 場景＋多方向角色圖 | 多方向角色圖、分層槍械、地圖與遮擋規則 | 可以360°射擊，但身體方向圖仍會切換，未能直接滿足整個人物平滑轉身。 |
| 3D 場景＋2D方向角色圖 | 模型環境、角色方向圖、槍械分層 | 場景有深度，但角色本身仍有方向圖切換。 |
| 3D 場景＋3D角色，像素風呈現 | 簡單模型、材質、骨架動作、固定鏡頭、渲染設定 | 可直接驗證連續轉身；需處理持槍姿勢、滑鼠投射與低解析度畫面穩定度。 |

目前製作建議改為第三種：優先做3D操作場，以簡單立體人形、槍及牆驗證鍵鼠與平滑轉身。固定傾斜鏡頭保留2.5D觀感，像素材質、配色與低解析度渲染共同形成像素風。原先「2D先行、4方向角色」的提案被本次更新取代，正式畫風仍待小樣評估。

Godot 支援將滑鼠畫面座標投射到3D場景，以及低解析度渲染後縮放呈現。這些是本方案的技術基礎；僅降低解析度不會自動得到理想畫風。UI及游標建議保持較高解析度，像素化僅作用於遊戲世界。[滑鼠投射與射線檢查](https://docs.godotengine.org/en/stable/tutorials/physics/ray-casting.html)、[多解析度呈現](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html)

### 3.2 規格卡

| 規格 | 現在要做什麼 | 暫用提案／完成條件 |
| --- | --- | --- |
| 首輪平台 | 選一個桌面測試平台 | 建議先以家中 Windows 開發機測試。 |
| 鏡頭取景 | 放主角、敵人、牆及障礙在同一個小場景比較 | 主角、瞄準方向與撤退路線可辨識。 |
| 角色比例 | 對齊角色、門寬、桌子及道路大小 | 兩名同伴能穿過原型所需通道，角色腳底位置一致。 |
| 像素基準 | 比較世界渲染解析度、材質像素密度及鏡頭距離 | 可先比較640×360與較細緻設定；數值為提案。UI獨立保持可讀，轉身時需檢查像素閃爍。 |
| 角色方向 | 連續360°轉身與瞄準 | 不把角度鎖到4或8方向；固定鏡頭不隨人物轉向。 |
| 持槍方式 | 模型的手部、槍及槍口使用一致的位置關係 | 是否穿身、槍口被牆遮住、近距離指向錯位；需轉一整圈檢查。 |
| 動畫範圍 | 暫用人形先連續轉身；再加持槍待機、行走與後退／橫移 | 先共用骨架與動作；受擊、倒下可暫用閃色和簡單姿勢。 |
| 字型與 UI | 實際顯示繁體中文、數字與標點 | 在預定視窗大小可讀、不缺字、不被截斷。 |
| 聲音規格 | 匯入小批聲音後對齊音量與用途 | 事件觸發正確，不突然過大、不重複疊播。 |

3D方案不需要為每個朝向各畫一套動畫，工作量改為模型、骨架、動作片段及像素材質。三位友方可先共用人形骨架與動作，再用外形和材質區別。3D角色照樣需要動畫整理；圖像生成能協助外觀參考、材質和圖示，無法直接代替模型與骨架製作。

## 6. 圖像生成與素材取得流程

### 6.1 第一批圖像工作提案

先準備一頁風格規格：固定視角、角色比例、色彩、光源方向、輪廓與材質表現。圖像生成先協助外觀／材質參考；實際遊戲小樣使用 **1 名匿名立體測試角色、1 個牆角、1 扇門、1 個箱子**，放到同一個場景比較。使用可轉向的模型來驗證，單張圖片不足以檢查連續轉身。

此批工作的完成點是「這套視角和比例適合玩」，角色並不因此定妝。圖片張數少，也便於替換不合適的方向。

| 工作 | 助手可負責 | 使用者主要決定 |
| --- | --- | --- |
| 風格規格 | 彙整尺寸、構圖、色盤及範例需求 | 喜歡的氛圍、清晰度、人物比例。 |
| 候選素材 | 撰寫提示、生成少量小樣、建立檔名及版本 | 從遊戲內效果挑方向。 |
| 素材整理 | 檢查模型比例、材質、骨架、圖示尺寸與匯入 | 若外觀不合喜好，指出原因。 |
| 動畫驗證 | 在不同轉向及移動方向實際播放，評估需修整之處 | 動作是否舒服、角色是否容易辨識。 |
| 玩法試玩 | 修正錯誤、提供測試場及操作說明 | 告知瞄準、移動及節奏的感受。 |

生成的概念圖與遊戲內素材分開驗收。材質需要合適的像素密度及映射；模型需有一致比例，腳底及武器掛點穩定，動作可播放；圖示需可用透明背景。低解析度畫面旋轉時可能有輪廓跳動及像素閃爍，需以實際遊戲測試調整。大張「像素風」插畫不算已完成可動角色或可用場景。

### 6.2 每份素材的記錄欄位

後續資源清冊使用以下欄位：

| 欄位 | 記錄內容 |
| --- | --- |
| ID／檔名 | 例如 CH-01；正式檔名採一致規則。 |
| 用途／首次使用批次 | 主角行走、R1 等。 |
| 規格 | 模型比例、材質尺寸、骨架／動作、腳底／掛點、格式；圖示另記像素尺寸。 |
| 來源 | 自製、生成紀錄，或下載頁與作者。 |
| 使用條件 | 授權、是否需署名、保存的授權文件。 |
| 狀態 | 待取得、暫用、待整理、已匯入、已實測、可正式使用。 |
| 驗證 | 哪個場景用過、還有何問題。 |

找到免費資源不等於已確認可用；以該份資源的實際條件記錄。初期採購數量為零，將預算留到明確知道缺少什麼時再決定。

## 7. 檔案與每次工作的交接

建議未來專案根目錄分為以下用途；目前尚未建立此結構：

```text
game/              Godot 專案、場景、腳本、實際匯入的資源
art-source/        美術原稿、生成候選、可編輯來源
docs/              企劃、規格卡、資源清冊、進度
licenses/          外部素材與字型的授權資料
builds/            可試玩的匯出版本
work/              可再產生的中間檔與驗證輸出
```

暫用素材與正式素材分資料夾，使用穩定 ID 讓替換時可追查用途。專案內的資源引用用相對路徑；目前這部電腦的絕對路徑不寫進遊戲邏輯。

每次週末工作結束，留一份短進度紀錄：

- 本次完成項目，以及可執行的專案／版本位置。
- 如何開啟與操作；Godot 的完整版本。
- 實際驗證結果；未做的互動測試另列。
- 新增或替換的資源及剩餘問題。
- 下一個具體工作項目。

若家中是另一部電腦，需把這批企劃文件帶到家中工作資料夾，並確認後續任務實際可讀取；不預設本機檔案已同步。

## 8. 建議執行次序與通過條件

| 順序 | 工作 | 交付物 | 通過條件 |
| --- | --- | --- | --- |
| 0 | 核對家中工具與建立工作位置 | 環境紀錄、固定專案路徑 | Godot 可啟動，專案檔可讀寫。 |
| 1 | 製作 R1 暫用3D操作場 | 專案、操作說明、驗證紀錄 | 鍵鼠移動、連續360°轉身與瞄準、射擊、遮擋、子彈時間及重設可用。 |
| 2 | 驗證像素風呈現小樣 | 渲染與素材規格卡 | 角色比例、槍口、遮擋、取景及轉身時的像素穩定度達到可用程度。 |
| 3 | 準備 R2 並串接功能 | 三人、相連路線、暫用事件、重試 | 即使沒有正式對白，也能走完功能流程。 |
| 4 | 依玩法整理正式需求 | 更新過的資源清冊 | 每份正式素材都有使用位置及規格。 |
| 5 | 製作 R3 並替換 | 一致美術、音效、介面 | 替換後功能仍可運作；敘事內容待使用者定稿再驗收。 |

整體遊戲的第一個可玩版本仍是三人逃難序章。此處將它拆成較小成果，讓週末可用時間和算力投入後都留下能接續的進度。

## 9. Goal 準備

Goal 適合寫明成果、驗證方式及範圍。官方文件以可檢查的證據作為完成依據；本案建議把第一個 Goal 設為「完成並驗證 R1 操作測試場」，之後再接三人流程。[Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

另有《回家後的第一個 Goal 草稿》，可在環境及工作位置確認後使用。目前沒有開始 Goal，也未指定算力預算；預算依使用者屆時設定。
