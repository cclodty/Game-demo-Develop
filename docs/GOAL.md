## 量體研究怎樣做（每張圖一樣；範本是 senado/README.md）
每張圖一個資料夾 massing/<id>/：README.md（研究報告，繁體中文）、site.json、data/osm_raw.json、data/massing.json、plan.svg、reference/photos/（Commons 照片，640 px）與 reference/photos/credits.json（檔名、作者、授權、網址）。衛星圖不入 git。README 要有：
1. 選址：為甚麼是這裏——航拍三秒認得出的特徵（附錄 A 的準則：靠地面圖案和輪廓，不是立面）、只有這裏才有的機制、敏感度；候選和落選的原因。
2. 範圍與座標：原點（OSM 點編號與經緯度）、軸向（X 東、Z 南、旋轉角與原因）、可玩範圍（闊 × 深）、周邊範圍（可玩範圍外 100–150 米，畫成背景的真實樓宇）。
3. 資料來源表：OSM（抽取日期、bbox、ODbL）、照片（Commons）、公開尺寸（網址）、衛星圖（只作對位，偏移量記下）、開發者實地量度（如有）。不用 Google 地圖、街景的圖（條款不准）。
4. 量度表：每項「名稱｜數值｜來源｜方法｜可信度（實測／OSM 標籤／照片估算／推算）」：街闊（牆到牆、路緣到路緣）、樓宇輪廓與高度、層數與層高、騎樓深度、地標尺寸、地面高度（每個平台、每段石階的級數與級高、斜路的坡度）、地面圖案（碎石路的方向與尺寸、賽道線、路肩、護欄顏色）、街道傢俬的位置（燈柱、路樁、長椅、樹）。照片量度用照片中的人（1.7 米）、門（約 2.1 米）或已知尺寸作比例，寫明用了哪一張。
5. 高低差與戰區：地面剖面圖；每個戰區的範圍與高度；通道；為甚麼這樣分。
6. 遊戲化改動表：每一處偏離實景（平面放大的倍數、移走的車、加闊的巷、合併的小樓、虛構的店名、為了頭目的路移開的街燈）、原因、對玩法的作用。沒寫在表上的偏離不准有。平面放大最多 1.25 倍（senado/README.md「比例」一節：實景的窄段對射擊遊戲偏窄），樓高照實；人物 1.78 米不變。
7. 遊戲用的東西：出生點在現實對應甚麼（巷口、門口、樓梯口、碼頭邊）、掩體在現實是甚麼（花槽、欄杆、攤檔、輪胎牆、繫纜樁）、這張圖獨有的機制、頭目構思（單人或雙人：最大戰區的外接範圍短邊 20 米以上算大場地；用到哪些地貌）。
8. checks：重建後 test/massing.test.mjs 要核對的量度，每項有數值、容差和量法（例如「福隆新街 x = 0 處的街闊：牆到牆 6.2 米 ± 0.3」「牌坊立面闊 23 米 ± 0.5」「前地到頂上平台的高度差 ± 0.3」「可玩範圍」「戰區高度」）。至少 8 項，涵蓋平面、高度、地標。
9. 待開發者到現場量或影的東西（可選；不等，總表列出）。
10. 對照圖：plan.svg（比例尺、北向、可玩範圍、戰區、現在的遊戲碰撞體疊在上面）；重建後再加一張「參考照片｜同一角度的遊戲截圖」並排。
研究做完：在 PR 貼 plan.svg 的截圖和量度表的重點；據研究寫重建卡和頭目卡（驗收用研究的數字），commit 了才開始重建。

## 三張虛構地圖的選址
- 準則：真實的澳門地點；航拍三秒認得出；有一個只有那裏才有的機制；平地或可以分層戰區；敏感度低（不用廟宇、政府機構、口岸、警署做戰場；賭場、酒店、商店的名字和招牌一律虛構；真實建築的量體可以有，招牌、商標、店名不放，同 senado-v6）。地圖 id（rooftop、club、docks）不變，名字改成真實地點，夜裏的時間（ROADMAP §6）照舊。揀一個、列兩個落選的，寫原因；總表寫「待開發者確認：選址」，然後照做，不停下來等。
- 天台（20:00）：例如舊區一排高度相若的唐樓天台（天台屋、水缸、晾衫竹、樓下的霓虹招牌架；排屋的天台要在容差內同高，否則分戰區或只取一幢）、工業大廈的大天台、外港客運碼頭的天台（停機坪在，但頭目不是直升機）。
- 夜店（21:00）：一幢真實大廈的輪廓與層高（OSM），室內佈局虛構但放得入那個輪廓，門口通出研究裏真實的街；例如新口岸的酒吧街一帶。店名虛構。
- 碼頭（01:00）：例如內港沿火船頭街的編號碼頭（查清有沒有真的「七號碼頭」，沒有就用真實的編號）、路環荔枝碗船廠（船排俯視很好認，屬文物，風格化）、筷子基一帶的碼頭。水邊（SPLASH）照留。

## 重建怎樣做
- 地圖資料由研究來：碰撞體（solids）按研究的輪廓與高度，在可玩範圍內沿街合併成牆；周邊範圍的真實樓宇畫成背景，合併成每種材質一個網格，取代 cityBackdrop 的假高樓；地面圖案用 textures.js 程序生成（不用照片做貼圖）。碰撞與外觀分開（CLAUDE.md）。
- 每張圖要有：`zones`、`rev`（加一）、`massing`（指向研究）、量度後寫入的 `budget`（開局 ≤ 600 次繪製、室內 ≤ 400，連兩架無人機在場也在內，test/drone.test.mjs）、`stages`、`spawns`（對應現實的入口）、`spots`、`fixtures`、`pads`、`hour`、`line`、`boss`、`camera`／`fade`（窄街用跟隨淡出）。
- 測試：test/massing.test.mjs 的 checks 全過；驗證器（出生點可達、道具不重疊、連通、對稱度）、戰區規則、瞄準誠實、渲染預算、地圖匯出一致；街機由它開局機械人打到第 4 波轉場；每日挑戰的測試；路線文字（test/route.test.mjs）；標題（test/title.test.mjs）；澳門一夜（test/night.test.mjs）。描述舊設計的斷言（例如「街闊 6 米、長 60 米」「看台上的人」「石階升 4.8 米」）改成新設計，同一個 commit，DECISIONS 記一行；仍然要的行為（例如「舖頭裏的玩家不會被撞中」若仍適用）不准刪、跳過或放寬。
- 截圖：俯視全圖對 plan.svg、預設鏡頭的遊戲視角、參考照片對同角度截圖。
- 單檔建置（npm run build）要在 16 MB 以內：量體資料只把遊戲用得着的部分寫進 src/（同 src/senado/data.js 的做法），原始資料留在 massing/。

## 頭目怎樣做
- 人，雙腳走路：不坐車、不駕駛、不飛、不躲在打不到的地方。名字與外形虛構（虛構幫派）；模型用方塊版或現有模型放大換色（刀后、重炮的做法），不加模型檔。
- 沒有「等」：一次無敵的時間（打中也不扣血）最多 3 秒，而且那段時間他在做一件玩家要應付的事；開打 15 秒內有第一次扣血的機會。測試量這兩個數字（每個頭目一個斷言）。
- 每個攻擊有看得見的預告（0.5 秒以上：紅線、紅圈、亮刀）；子彈時間是看清楚再解的工具，不是保命符。
- 至少三種漂亮的解法：一種用到這張圖的地貌（研究裏寫的），一種不開槍（踢、鑊、人盾、環境）。
- 雙人：互補（一遠一近、一盾一炮、一封路一追擊）；導演錯開預告（同一時間只開始一個新預告），合招除外：合招有名、有預告、有解法，是用子彈時間解的題目；倒下一個，另一個變招（第一版：快 20%、多一招，變招前 1.5 秒停下來，是扣血的窗口）；兩條血條；兩個都倒才結算。
- 格數：單人中段（第 4、8 波）3 格、最後（第 12 波）5 格（現在的）；雙人每人中段 2 格、最後 3 格（第一版）。獎勵照 waves.js 的 midBoss（中段 +1,000、最後 +2,000）。
- 一局十分鐘：機械人由每個起點打完整局（test/arcade.test.mjs 的 15 分鐘上限）仍然通關；機械人要學會每個新頭目的打法（test/helpers.mjs）。
- 舊的 kind（heli、convoy、truck、dj）留在 boss.js 作可選，不上場；它們的測試自己把它們放回一張地圖（test/dj.test.mjs 是例子），照舊要過。

## 分支與 PR（開發者的做法）
1. 用被指派的分支。開工時先照「第一步」合併 main、PR #19、這份提示詞的分支（merge，不 rebase）。每張卡開工前 git fetch，有新 commit 就合併。
2. 第一次 push 時開一個草稿 PR（標題「第四階段：一夜 ②：實地重建」；分支已有開着的 PR 就用它，改標題和描述），之後每張卡累加一段並更新頂部總表；不另開 PR。開發者說「合併吧」之類的話：把 PR 標為可審，用合併提交（英文標題、一段中文內文）合併進 main，再把工作分支快轉到 main（git checkout -B <分支> origin/main，普通 push，不 force）繼續，餘下的卡開新 PR；告訴開發者 Pages 部署好了、要強制重新載入。開發者沒說就不合併；永遠不 force-push、不 rebase 已推送的歷史。
3. 每張卡做完就 push，CI 綠了才 push 下一張；等 CI 時可以在本機先做下一張（只是不 push）。CI 紅就修到綠：修正排在下一張卡之前；不准刪、跳過或放寬測試。
4. PR 描述照 .github/pull_request_template.md；每張卡的那一段寫「玩家會感受到什麼不同」、逐項打勾的驗收、手感數字、截圖；頂部總表每卡一行：卡名｜狀態｜新增測試數｜截圖｜待開發者確認的事。開發者只看這張表和截圖。

## 一張卡的流程
1. 從 docs/TASKS.md 拿次序上的下一張未打勾、不是標給「開發者」的卡。先在回覆裡複述它的驗收標準和「這次不做」，也對照 ROADMAP 與研究裏同一項的設計意圖。
2. 先寫測試（新行為必有測試，放 test/），跑一次確認它真的紅，再實作。
3. 跑 npm run lint && npm test；改了敵人、武器、拾取、波次、頭目、地圖、模式或轉場，加跑 npm run test:game。全綠才 commit。整套測試在背景跑時不要改 src/ 或 test/；容器重啟或測試中途被停，就重跑，不用一半的結果。
4. 玩法或畫面有改就截圖到 test/.out/。PR 用的圖轉成 JPEG（品質 82）放 docs/shots/phase-4b/，在 PR 描述用該 commit 的 raw 連結引用。研究要有 plan.svg 的截圖；重建要有俯視全圖、遊戲視角、照片對照。
5. 改了 config.js 或資料裡的手感數字，就在 docs/DECISIONS.md 記舊值→新值和原因（一卡一行，連「為什麼」）。數字都是「第一版，待試玩確認」。
6. 在 docs/TASKS.md 把卡的標題加 ✅ 和日期，驗收項目逐項打勾。發現的事加到「待排」，不要動手做。
7. commit（英文、說清楚為什麼；結尾照環境給的署名行）、push、更新 PR 描述，然後下一張。

## 技術上要守的
- 遊戲邏輯只用 game.rng，不用 Math.random；特效用 utils.js 的 rand。邏輯在 120 Hz 固定步裡運行，新系統放進 logic，不放 present。一局留下的東西要在 resetWorld／resetProps 重設（test/seed.test.mjs 會抓）。
- 輸入只從每步的 game.cmd 讀；瞄準點是 StepInput 的一部分，改瞄準的算法只改「怎樣由畫面得出瞄準點」，邏輯照讀 cmd。新動作盡量重用現有控制；真的要新控制就加在 input.js BUTTONS 的最後，記錄格式版本號跟着升，重播測試要過。
- 戰區、通道、頭目的路與站位、合招、賽車的時間表、地圖的 rev 都是地圖資料（maps.js），行為寫在系統（level.js、enemies.js、waves.js、boss.js、bullets.js）。不寫「只有這張地圖才有」的程式。
- 地圖 id 與 MAPS 的次序不變（重播、每日輪替、排行榜、澳門一夜都靠它）；地圖數目這一輪不變，所以 backend/worker.js 的 LIMITS.maps 不用改。
- 每張地圖「恰好四盞點光源」照舊（CLAUDE.md）；新材質過 addCutaway 與 game.style.dress()；?style=off 必須玩起來完全一樣；議事亭的平塗畫風（look: 'flat'）照舊。
- 繪製次數：佈景合併成幾個網格（mergeGeometries）或 InstancedMesh；道具模型載入時自動按材質合併（models.js mergeByMaterial）。可見與否、合併的範圍不能取決於特效隨機數（test/maps.test.mjs 每張圖載入四次要一樣）。
- 會動的危險（賽車、滾落的油桶）沿資料裡的路或時間表走，預告比危險早到，用世界時間。
- 不加執行期依賴（開發依賴可以，大的先問）；不碰 senado/（只讀它的資料和 README）；不換引擎；repo 裡不放密鑰與個人資料；commit 與程式不寫模型名。真實地點，其餘全部虛構：幫派、人名、店名、招牌、車隊、贊助、賭場名。
- 授權：OSM 資料（ODbL）要署名：massing/<id>/README.md、遊戲內現有的署名處（議事亭已有，照樣加上新地圖）、README。照片只放 Commons 上可再用的，連作者與授權；衛星圖不入 git。

## 寫測試要避開的坑（之前 CI 紅過或本機反覆過的原因）
- 不要斷言取決於隨機冷卻的時間點。用固定種子（?seed=）並逐格檢查狀態。
- 擺位後先把被擺位過程影響的狀態重設，再開始量度（killcamT、hitstopT、焦點；敵人用 e.update = () => {} 定住）；敵人生成後有 spawnLock，先設為 0；測試裡的子彈要給它飛的時間（60 m/s 在 120 Hz 一步飛半米）。
- 測試裡按鍵：helper 每步會清掉 input.pressed，要在那一步開始前加；WASD 是「畫面上下左右」，跟鏡頭的方向轉。
- page.reload() 之後 window.game 是 <div id="game"> 直到 main.js 接手：先 waitForFunction(() => window.game && typeof window.game.startRun === 'function')。每個 h.open() 是新的瀏覽器環境；同一頁 reload 才共用 localStorage。開兩個頁面的測試先停掉第一個頁面的畫面循環，頁面在 try/finally 裡關閉。
- 一個被動的玩家（不走動）要能被打死：敵人走不到、射不到玩家時一波會打不完（東望洋跑道的看台試過一次）。戰區規則令不同層的敵人不開槍，所以他們一定要走得到玩家那一層：每張圖改完跑一次每日挑戰的測試。
- 列出所有模式或所有地圖的測試（beats、night、title、guia、ruins、route）：改地圖時一併改，這是跟着設計改，不是放寬。
- 規則（setRules）到下一局 startRun 才生效：測試改過規則，收尾時改回 'normal' 並開一局。
- 特效隨機數每頁一個隨機種子：繪製次數、可見與否不能取決於它。
- 不要用 Date.now 或系統時鐘決定測試結果；每日挑戰的測試要能注入日期。
- 測試不准連網（量體資料入 git）；未完成的測試草稿不要放進 test/。
- 兩組重的瀏覽器測試不要同時跑；截圖腳本單頁可以。
- CI 分三份同時跑，最長一份約 14 分鐘；本機 npm test 約 35 分鐘（約 320 個測試），test:game 約 10 分鐘。容器可能重啟，背景的測試會停：重跑。
