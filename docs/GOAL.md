# /goal 提示詞：把第一階段「一局」做完

貼給 /goal 的全文在下面的框內。執行者可以是一個全新的 Claude 對話：它只有這個 repo，沒有之前對話的記憶。所以所有規矩都指回 repo 裡的檔案，做到哪裡也以 repo 和 PR 為準。

第二版，2026-10-18：前九張卡已經在 `goal/phase-1` 上做完，這一版接著做餘下四張，並寫進第一版跑下來學到的做法。第一版的全文在這個檔案的 git 歷史裡。

```
目標：依 docs/TASKS.md，把《子彈芭蕾》第一階段「一局」餘下給 Claude 的任務卡逐張做完，交出一個可以給五個人試玩的版本。

開始前先讀 CLAUDE.md、docs/ROADMAP.md、docs/TASKS.md、docs/DECISIONS.md。所有規矩以 CLAUDE.md 為準；這份提示詞只補充怎樣連續工作。回覆用繁體中文。

## 現況
- 分支 goal/phase-1，PR「第一階段：一局」（cclodty/Game-demo-Develop#10，草稿）已開。接著用，不要開新分支或新 PR。
- 已做完、不要重做：新模型校正、確定性①②、街機模式①②、Style 即時評級、60 秒新手熱身、木箱與白鴿、滑鏟、盾牌手，以及更早的旋轉換彈、擲物、效能預算、風格系統。
- 開發者 2026-10-17 決定不再用 Dots 做人物；第一階段用現有模型。自建人物模型在待排，不屬這個目標。

## 分支與 PR
1. 只用這一個 PR。不要合併到 main，不要開第二個 PR，不要 force-push；合併由開發者決定。
2. 每張卡做完就 push，等 CI 綠才開始下一張。CI 紅就修到綠；不准刪、跳過或放寬測試來過關。
3. PR 描述照 .github/pull_request_template.md，每做完一張卡就累加一段，並更新頂部總表。

## 一張卡的流程
1. 從 docs/TASKS.md 拿下一張未打勾、不是標給「開發者」的卡。先在回覆裡複述它的驗收標準和「這次不做」，也對照 ROADMAP 裡同一項的設計意圖。
2. 先寫測試（新行為必有測試，放 test/），再實作。
3. 跑 npm run lint && npm test；改了敵人、武器、拾取、波次或轉場，加跑 npm run test:game。全綠才 commit。
4. 玩法或畫面有改就截圖到 test/.out/。PR 用的圖轉成 960 px 寬的 JPEG，放 docs/shots/phase-1/，在 PR 描述用 commit SHA 的 raw 連結引用。
5. 改了 config.js 或資料裡的手感數字，就在 docs/DECISIONS.md 記舊值→新值和原因。新敵人、新規則的數字是「第一版，待試玩確認」。
6. 在 docs/TASKS.md 打勾（寫日期）。發現的事加到「待排」，不要動手做。
7. commit（英文、說清楚為什麼）、push、更新 PR 描述，然後下一張。

## 次序
炸彈客 → 變體規則與難度 → 最佳片段錄影 → 本機事件記錄。

## 技術上要守的
- 遊戲邏輯只用 game.rng，不用 Math.random；特效用 utils.js 的 rand。邏輯在 120 Hz 固定步裡運行（main.js 的 step/logic），新系統放進 logic，不要放 present。一局留下的東西要在 resetWorld／resetProps 重設（test/seed.test.mjs 會抓）。
- 風格層 src/style.js 只管渲染。新加進場景的東西要過 game.style.dress()；新的人物姿勢程式要經 style.poseDue()。?style=off 必須玩起來完全一樣。
- 新內容放資料（enemies.js TYPES 含 spawn 出場規則、maps.js、weapons.js、waves.js MODES、新的 rules.js），新行為放系統。
- 每張地圖有渲染預算（maps.js budget）。超出就減東西，不要調高預算。
- 不加執行期依賴（MediaRecorder、localStorage 是瀏覽器內建，可以用），不碰 senado/，不換引擎。

## 寫測試要避開的坑（第一版 CI 紅過的原因）
- 不要斷言取決於隨機冷卻的時間點。要用固定種子（?seed=）並逐格檢查狀態，例如「未瞄準時沒有提示，開始瞄準那一格有提示」。
- 擺位後先把被擺位過程影響的狀態重設（鴿群、blindT 等），再開始量度。
- 敵人生成後有一段鎖定期（spawnLock），期間子彈會穿過。測試要先等它過去，或者手動把 spawnLock 設為 0。
- 開兩個頁面的測試，要先停掉第一個頁面的畫面循環（g.frame = () => {}），否則第二個頁面在 SwiftShader 下要幾分鐘才開得起。頁面一律在 try/finally 裡關閉。
- 未完成的測試草稿不要放進 test/：npm test 會把它一起跑。

## 需要人判斷的事
- 手感與平衡的數字：用卡上或 ROADMAP 的預設值做完，在總表標「待試玩確認」，繼續下一張，不要停下來等。
- 卡上要開發者量的東西（例如錄影對真機 fps 的影響）：做好量度的方法和 SwiftShader 下的數字，真機數字列為「待開發者確認」，不要因此停下。
- 標給「開發者」的項目（合併 PR、試玩、決定日）：跳過，不要替開發者做。

## 停止條件（停下來，在 PR 描述頂部寫明原因，然後結束）
- 同一張卡連續兩次 CI 紅，而找不到原因。
- 需要新的執行期依賴、要改 senado/、要付費、要開帳號、要放密鑰。
- 清單上給 Claude 的卡全部做完：在 PR 頂部寫第一階段的總結（做了甚麼、所有「待試玩確認」和「待開發者確認」的事一次列齊、試玩前建議先看哪幾項），然後結束。

## 進度回報
PR 描述頂部維持一張總表，每張卡一行：卡名｜狀態（做完／進行中／跳過及原因）｜新增測試數｜截圖｜待開發者確認的事。開發者只會看這張表和截圖，所以要寫給不在場的人看。
```

## 使用方法

1. 把框內全文貼進 /goal。
2. 它會在 `goal/phase-1` 上一張一張做，PR 就是進度表；隨時可以手動停止。
3. 停了之後要續做，貼同一段提示詞即可，它會從 TASKS.md 未打勾的卡接著做。
