## 分支與 PR（開發者的做法）
1. 用被指派的分支，由最新的 main 開始（PR #19 已合併）。每張卡開工前 git fetch origin main，有新 commit 就合併進來。
2. 第一次 push 時開一個草稿 PR（標題「第四階段：一夜 ②」）（「一夜 ①」的總結已在 PR #19 頂部），之後每張卡累加一段並更新總表；不另開 PR。開發者說「合併吧」之類的話：把 PR 標為可審，用合併提交（英文標題、一段中文內文）合併進 main，再把工作分支快轉到 main（git checkout -B <分支> origin/main，普通 push，不 force）繼續，餘下的卡開新 PR；告訴開發者 Pages 部署好了、要強制重新載入。開發者沒說就不合併；永遠不 force-push、不 rebase 已推送的歷史。
3. 每張卡做完就 push，CI 綠了才 push 下一張；在等 CI 時可以在本機先做下一張（只是不 push）。CI 紅就修到綠：修正排在下一張卡之前；不准刪、跳過或放寬測試。
4. PR 描述照 .github/pull_request_template.md；每張卡的那一段寫「玩家會感受到什麼不同」、逐項打勾的驗收、手感數字、截圖；頂部總表每卡一行：卡名｜狀態｜新增測試數｜截圖｜待開發者確認的事。開發者只看這張表和截圖。

## 一張卡的流程
1. 從 docs/TASKS.md 拿次序上的下一張未打勾、不是標給「開發者」的卡。先在回覆裡複述它的驗收標準和「這次不做」，也對照 ROADMAP 裡同一項的設計意圖。
2. 先寫測試（新行為必有測試，放 test/），跑一次確認它真的紅，再實作。
3. 跑 npm run lint && npm test；改了敵人、武器、拾取、波次、模式或轉場，加跑 npm run test:game。全綠才 commit。整套測試在背景跑時不要改 src/ 或 test/；容器重啟或測試中途被停，就重跑，不用一半的結果。
4. 玩法或畫面有改就截圖到 test/.out/。PR 用的圖轉成 JPEG（品質 82）放 docs/shots/phase-4/，在 PR 描述用該 commit 的 raw 連結引用。新地圖要有俯視全圖和一張遊戲視角的截圖；改繪製次數的要有前後對比。
5. 改了 config.js 或資料裡的手感數字，就在 docs/DECISIONS.md 記舊值→新值和原因（一卡一行，連「為什麼」）。數字都是「第一版，待試玩確認」。
6. 在 docs/TASKS.md 把卡的標題加 ✅ 和日期，驗收項目逐項打勾。發現的事加到「待排」，不要動手做。
7. commit（英文、說清楚為什麼；結尾照環境給的署名行）、push、更新 PR 描述，然後下一張。

## 技術上要守的
- 遊戲邏輯只用 game.rng，不用 Math.random；特效用 utils.js 的 rand。邏輯在 120 Hz 固定步裡運行，新系統放進 logic，不放 present。一局留下的東西要在 resetWorld／resetProps 重設（test/seed.test.mjs 會抓）。
- 輸入只從每步的 game.cmd 讀；新動作盡量重用現有控制；真的要新控制就加在 input.js BUTTONS 的最後，記錄格式版本號跟着升，重播測試要過。
- 互動件、門、水邊、工具、舞台、頭目的路、賽車的時間表、高低差都是地圖資料（maps.js），行為寫在系統。不寫「只有這張地圖才有」的程式。
- 頭目：Boss 子類登記在 boss.js 的 BOSSES，地圖用 `boss: { kind, … }` 選。加頭目時 waves.js 的 bossWave、main.js 的路線文字（routeText）、test/route.test.mjs、test/boss.test.mjs、各地圖的整局測試都要跟着；機械人（test/helpers.mjs）要打得贏它，整局測試仍然通關。
- 高低差（大三巴）：地圖給 `ground(x, z)`（level.js groundY）和 `slope`；所有畫出來的東西畫在「離地高度＋該點地面高度」；站在高處的人用 `over` 越過矮過他的掩體看和射；鏡頭、瞄準平面、切走都跟玩家腳下的地面；掩體的模型由腳下的地面量起。燈塔山頂沿用同一套。

## 寫測試要避開的坑（之前 CI 紅過或本機反覆過的原因）
- 不要斷言取決於隨機冷卻的時間點。用固定種子（?seed=）並逐格檢查狀態。
- 擺位後先把被擺位過程影響的狀態重設，再開始量度（killcamT、hitstopT、焦點）；敵人生成後有 spawnLock，先設為 0；測試裡的子彈要給它飛的時間。
- 測試裡按鍵：helper 每步會清掉 input.pressed，要在那一步開始前加；WASD 是「畫面上下左右」，跟鏡頭的方向轉。
- page.reload() 之後 window.game 是 <div id="game"> 直到 main.js 接手：先 waitForFunction(() => window.game && window.game.startRun)。每個 h.open() 是新的瀏覽器環境，localStorage 不共用；同一頁 reload 才共用。
- 一個被動的玩家（不走動）要能被打死：敵人走不到、射不到玩家時一波會打不完（第四階段 ① 的看台就是這樣，每日挑戰的測試捉到）；新地圖加完跑一次每日挑戰的測試。
- 列出所有模式或所有地圖的測試（beats、night、title、guia、ruins 數卡）：加模式或地圖時一併改，這是擴展，不是放寬。
- 規則（setRules）到下一局 startRun 才生效：測試改過規則，收尾時改回 'normal'。
- 特效隨機數每頁一個隨機種子：繪製次數、可見與否不能取決於它。
- 兩組重的瀏覽器測試不要同時跑；截圖腳本單頁可以。
- CI 分三份同時跑，最長一份約 14 分鐘；本機 npm test 約 35 分鐘（320 個測試），test:game 約 10 分鐘。容器可能重啟，背景的測試會停：重跑。

## 使用方法

1. 試玩 PR #18、#19 的內容（記得強制重新載入）；有回饋就寫進 docs/TASKS.md「試玩回饋 ④」（或用遊戲的匯出交給 Claude 寫卡）。兩個 PR 都已合併，新對話由 main 開始，一開頭就讀得到這份提示詞和重新整理過的 ROADMAP。
2. 開新對話，把「短版」框內全文貼進 /goal。它會讀「完整工作規矩」，先看試玩回饋，再寫卡、按次序做。
3. 你在另一個對話改的東西：推上 main 就好，它每張卡開工前會合併 main。
4. PR 就是進度表；隨時可以手動停止。寫卡那一步做完就值得看一眼卡，覺得方向不對可以即時改 TASKS.md 或叫停。
